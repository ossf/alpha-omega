# October 2026

October’s work focused on strengthening registry operations, continuing to refine the Organizations feature, and coordinating security findings with gem maintainers. The team completed a major database upgrade, greatly expanded logging capabilities and resolved a high number of security reports for [rubygems.org](http://rubygems.org) itself.

## Private Beta for Organizations

### Gem Publishing Support

We added support for newly created gems to be associated with an organization when published. Maintainers provide organization metadata in the gemspec, and the gem is owned by the organization from its first release. Previously, new gems defaulted to being owned by the user pushing them, which meant organizations had to transfer ownership after the fact and left a window where a gem was tied to an individual account.

### Prefix Reservations

We launched an alpha version of prefix reservations, building on the gem-name reservations introduced last month. The core use case is organizations that name their gems in a predictable pattern, such as aws-sdk-\*. A reserved prefix can only be used by the owning organization: pushing a new gem that matches a registered prefix returns a 403 error unless the organization’s metadata is set in the gemspec. This gives organizations a practical way to prevent lookalike or dependency-confusion packages from appearing under names they use. Prefixes are not yet available through the UI and are set and managed by a RubyGems admin, which lets us work through policies on limits and fairness before opening them up more broadly.

We shipped a number of improvements to UI workflows based on feedback from beta participants. 

We onboarded another organization and held a customer interview with them, which brings us to 17 active organizations.

## Package Repository Security

### Displaying Security Warnings

RubyGems.org now ingests the OSV database and displays a warning message to users on affected packages, with links to the source vulnerability report.  You can read more about this feature on the RubyGems blog, [rubygems.org now shows security warnings for gems](https://blog.rubygems.org/2026/10/15/rubygems-org-now-shows-security-warnings-for-gems.html). 

### Email Confirmation & MFA hardening

After hardening the password reset system, we also made similar changes to the email verification flows by hardening confirmation token handling, improving CSRF protection, adding MFA rate limiting and tightening challenge handling.

### Authenticated-page cache safeguards

We strengthened cache behaviour by ensuring that authenticated responses instruct CDNs not to cache them.

## Infrastructure Security

### Postgres Upgrade 14 to 18

The team carefully prepared, tested and executed a new zero-downtime database upgrade process successfully across staging and production for rubygems.org. Extensive preparation and testing were required to ensure such a large jump could be done safely in one go and consumed a large portion of the month for Issy and Dushan. The new process is fully documented and codified in Terraform and we are very confident executing it for all future cases.

It was essential to complete this work prior to October 31st when a forced reboot of the production RDS would have occurred. This deadline has been met and [rubygems.org](http://rubygems.org) is running happily on Postgres 18\.

The upgrade itself takes [rubygems.org](http://rubygems.org) from PostgreSQL 14, which leaves community support on November 12th and would have started costing Extended Support fees from March, onto one supported until 2031, with faster vacuum, cheaper `IN` list lookups, skip scans on multicolumn indexes and asynchronous I/O.

### Log retention

The log storage project has concluded. Security-relevant logs from [rubygems.org](http://rubygems.org) and AWS are now retained for 365 days.  These logs are enriched with actor identities ([https\://github.com/rubygems/rubygems.org/pull/6822](https://github.com/rubygems/rubygems.org/pull/6822)) and other relevant context ([https\://github.com/rubygems/rubygems.org/pull/6850](https://github.com/rubygems/rubygems.org/pull/6850)) and are easily searchable within Datadog. Logs are archived in S3 with robust guardrails against accidental or malicious deletion.

### Memcache and Kubernetes

The team also completed scheduled maintenance of other critical services for [rubygems.org](http://rubygems.org), notably updating a very old and outdated Memcache instance to the latest version.

In response to the eMudhra certificate disclosures, we upgraded our EKS cluster and rotated all EC2 instances running [rubygems.org](http://rubygems.org) workloads.

## AI Security Engineers in Residence

While September focused on scanning, October focused on remediation. The team worked through scanner output for 10 gems, assessing 55 individual findings. Of these, 52 were rejected as not exploitable and 3 were confirmed as real vulnerabilities. Four new vulnerability reports went to maintainers, and one was accepted within the fortnight. Four follow ups drew four maintainer responses. One severity was downgraded before reporting, one duplicate was closed without contact, and one non vulnerability was pushed upstream as a public hardening PR. As expected, no new scans were started while we continue to work through a large findings backlog.

[Kou](https://github.com/kou), our Ruby Core member, verified two findings from his Scrutineer scans, one in Ruby’s Marshal implementation and one in the openssl gem’s SNI implementation. Neither is a vulnerability, since Marshal.load is unsafe by design and the openssl gem does not provide enough features for SNI to be exploitable. He fixed the Marshal finding in [ruby/ruby\#19550](https://github.com/ruby/ruby/pull/19550) and is working on the openssl finding in [ruby/openssl\#1125](https://github.com/ruby/openssl/issues/1125), so neither will later surface as a false positive security report.

Kou also handled a StringScanner report received through HackerOne. It was a crash bug rather than a vulnerability, so he reviewed the reporter’s patch and merged it in [ruby/strscan\#220](https://github.com/ruby/strscan/pull/220). He is currently reviewing an RDoc report submitted through security@ruby-lang.org, which is expected to be handled as a non vulnerability.

### Registry Vulnerabilities

We also handled a sharp rise in inbound security reports for RubyGems.org. This shifted some of the team’s time to reviewing and resolving these reports. The work resulted in 4 GitHub security advisories, with another issue under embargo that we expect to release soon.
