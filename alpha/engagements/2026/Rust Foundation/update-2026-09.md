### Disclosure at scale

This month produced a [debate](https://rust-lang.zulipchat.com/#narrow/channel/613087-security-chat/topic/Ecosystem-wide.20disclosure.20.2F.20mass.20filing.20LLM-found.20issues/with/626666235) on how to handle vulnerability reports generated by AI tools at ecosystem scale. There is still discussion to be had, but there may be some convergence on a process of filing issues publicly by default, from a standard template, reviewed and filed by a human, and reserving embargo for cases with clear evidence of exploitation, on the grounds that embargoed contact costs five to ten times the effort of a public issue and rarely changes the outcome. What the threshold should be is an open question.

## Curation Overlays

Our grant proposal for discovery work on curation overlays has been approved by Alpha-Omega (thanks\!). Dirkjan Ochtman will lead an effort responsible for the discovery and prototyping of a Rust Ecosystem Curation program, which, when implemented, will be a cohort of crates chosen for their criticality to the ecosystem with heightened supply chain security practices and staffed vulnerability coordination behind them. The idea is a layer downstream of crates.io that can apply patches of last resort, holds, and license or scan rules as composable feeds,  drawing on existing curated sets examples from folks such as Ferrous Systems' and via `cargo-vet` audits.

## Signing and Mirroring

It was demo month, and the Foundation also [introduced Arlo Siemsen](https://rustfoundation.org/media/meet-arlo-siemsen-distribution-engineer-for-the-rust-supply-chain/) publicly this month as a Distribution Engineer for the Rust supply chain, generously funded by Alpha-Omega.

The shape of the architecture continues to settle, including TUF metadata in Git and artifacts in object storage, signing performed outside GitHub Actions in ephemeral compute, etc.

Arlo and Walter gave the first public demos of the work they were doing. Walter showed [`rustup`](https://github.com/rf-signing-experiment/rustup/tree/tbdsigning) fetching channel manifests through TUF and Arlo showed Cargo verifying crates against a Merkle tree. The demo was generally received favorably, including the rustup integration, storing the signing key in the TUF repository and generally decoupling crates.io from TUF as much as possible. There is a question around DSSE, and the team is considering the standard TUF JSON format. This work is done in a fork of [`rust-tuf`](https://github.com/rf-signing-experiment/rust-tuf/tree/tbdsigning) by Arlo. Also, a rust implementation of `tuf-on-ci` is being [crafted](https://github.com/rf-signing-experiment/tufops) for the Rust Projects specific needs.  
We are moving closer and closer to being able to host a usable mirror based on this work.

## Targeted Social-Engineering Campaign

We had a serious security event this month which was a sustained social-engineering campaign against high-profile Rust maintainers. It took the form of a fake job/technical interview invitation that asks the target to clone and run a repository, following the same playbook as the August `arrayref` compromise. Several maintainer accounts were compromised before the campaign was identified. The crates.io and security response working group published a joint [post](https://blog.rust-lang.org/2026/09/17/targeted-attacks/) describing the campaign and what maintainers should watch for.

From the Foundation side, Adam Harvey and Walter Pearce helped lead the response. Datadog dashboards now track the actors' activity against crates.io in near real time, and a second pulse of activity surfaced a further set of accounts that are being actioned.

To help combat this type of activity in the future, we are looking at arranging anti-phishing training for Rust Project maintainers. We are also looking to increase Datadog log retention as attackers in these campaigns typically wait a while between gaining access and acting, and our current live-log retention window loses that history.

## Rust Foundation Security Policy

The [Rust Foundation Security Policy](https://rustfoundation.org/policy/security-policy) is now [published](https://rust-lang.zulipchat.com/#narrow/channel/335408-foundation/topic/Blog.20Alerts/near/624766991) and live. The EU Cyber Resilience Act (CRA) reporting obligations for manufacturers began on 11 September 2026\. Open-source stewards such as the Foundation are not required to comply until 11 December 2027, but publishing now lets the policy be exercised and refined well before then. It defines how to report a vulnerability in Foundation-operated services and subsequent actions.

Ubi suggested surfacing the security policy from every Foundation repository through GitHub community-health files. We will look into that.

## crates.io Quarantine

Jess is drafting a quarantine RFC, including "held" and "withdrawn" statuses in the Cargo index metadata plus crates.io admin bulk APIs, with a second RFC on an automated review queue to follow. A possible sequence here is quarantine support in the index, registry and Cargo, crates.io support for manual administrative quarantine, and bulk actions to replace today's ad-hoc database operations, with Adam advising on the admin API design.

## Rust/C++ Interop

teor's [initial draft analysis](https://github.com/rust-lang/goals/issues/643#issuecomment-5832453934) of the C++ standard library shows that potentially 80–95% of its overloads can be represented in Rust with an experimental overloading macro. The impact here is that future automated generation of Rust to C++ bindings becomes easier and more ergonomic. So every overload the macro handles can alleviate the need for someone to write a custom piece of unsafe glue code. (Currently, some interop binding generation tools automatically or manually rename overloads in Rust, while others require the user to manually write glue code for each overload.)

Ian McCormack (Carnegie Mellon) [circulated](https://rust-lang.zulipchat.com/#narrow/channel/427678-t-lang.2Finterop/topic/BorrowSanitizer.20pre-MCP/with/626518944) an [MCP draft](https://hackmd.io/@icmccorm/BJjVhTIFMg) for upstreaming BorrowSanitizer on the Rust side after conversations at RustConf. In addition to BorrowSanitizer’s Rust and C/C++ checks, there is a related MCP for [distributing clang in rustup](https://github.com/rust-lang/compiler-team/issues/907), which will help reduce accidental interop miscompilations due to incompatible LLVM versions in rustc and clang, particularly when using LTO.
