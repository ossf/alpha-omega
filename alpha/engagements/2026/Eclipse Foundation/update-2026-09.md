# Incident Management and Response

* GitLab Exploited (CVE-2026-85706, CVSS 10.0): A path-traversal flaw disclosed 10 September was blocked the next evening, but an undocumented endpoint the advisory omitted left the files reachable, so exploitation ran 12-14 September behind a mitigation that only looked effective until the team's logs revealed the real path. The fix shipped for 19.x alone, forcing an 18.x migration, completed 16 September.  
* Exposure Contained: Master encryption and signing keys, service passwords and the SSO/OAuth secret were copied, but the attacker got no further than reading files. Network isolation kept the database out of reach and session validation made the keys unusable: no account takeover, code execution, persistence or tampering followed. All credentials were rotated, sessions invalidated and tokens revoked.  
* Follow-Through: A later GitLab flaw was patched within an hour; the incident also served as a Cyber Resilience Act reporting tabletop.  
* Full account can be found in the following blog post: [https\://mikael.barbero.tech/blog/post/2026-09-25-gitlab-cve-2026-85706-exploitation/](https://mikael.barbero.tech/blog/post/2026-09-25-gitlab-cve-2026-85706-exploitation/)

# Vulnerability Management

* Continuous Report Handling Support: Supporting projects through their vulnerability reports handling remained steady background work across the month, carried by the L1 rotation \- following up on outstanding reports, chasing responses where projects had gone quiet, and working through the standing backlog of open advisories alongside newly reported findings.  
* Committer Guidance Drafted: A vulnerability handling document for committers was written and taken through team review. It covers the processes committers most often ask about, including how to request a CVE, and will be published shortly.  
* Feedback Loop Established: A feedback form is now attached to closed vulnerability reports, letting maintainers record what they found useful about the process and what was off, selecting as many of each as apply. 

### Scanning Campaigns

* First Campaign Cycle Closed Out: The last 300 findings from the first vulnerability scanning cycle were validated and reported, concluding it.  
* Second Cycle Launched Under Project Glasswing: The Foundation announced its participation in Anthropic's Project Glasswing on 9 September, opening enrollment for priority security reviews running through October 2026\. Projects enroll by merge request to a public repository ([https\://gitlab.eclipse.org/eclipsefdn/security/ai-scan-enrollment](https://gitlab.eclipse.org/eclipsefdn/security/ai-scan-enrollment)), with enrollment prioritizing rather than exempting, as all projects will eventually be reviewed.

### Triage Tooling

* L1 Helper Extended: The L1 helper gained threat model generation from validated scan data, findings export, and generation of remediation patches as diffs tested in sandbox environments. Patch delivery by diff was adopted over automatically opening private forks and pull requests, as the less intrusive mechanism. A monitoring mechanism was built to automatically restart stuck or failing scans.  
* Duplicate Finding Suppression: Shared state was introduced behind Scrutineer so that re-scanning a project no longer re-reports findings already raised. It was seeded with previously reported findings from both GitLab and GitHub, and a duplicate check now runs before anything reaches a project.

# SBOM

### Infrastructure

* Migration to PIA: Of 77 upload targets in DependencyTrack, 34 required migration off Otterdog, the remainder being direct uploads or inactive projects. Pull requests now cover every one: 35 in all, 22 are merged and fully migrated, 8 await merge, and 5 remain in draft pending confirmation of changed project hierarchies and the matching authorization in PIA. Counting seven targets switched ahead of the campaign, 29 now publish through PIA.  
* Upload Size Limit Surfaced: An SBOM too large for the upload limit was identified during migration. We are working on addressing this limitation.

### PIA

* SBOM Upload Repaired: The upload workflow had never executed since being added in August, so no SBOM had ever reached DependencyTrack from CI. It was converted to a reusable workflow called from the publish run itself, taking the version from image metadata rather than a suppressed event ([PR \#94](https://github.com/eclipse-csi/pia/pull/94)).  
* Workload Identity Allowlist: The OIDC event allowlist had accidentally blocked legitimate uploads from two projects. `release` and `schedule` were added after assessment against the same bar as the existing entries, restoring normal operation, and rejection responses now name the rejected claim and the allowlist so a maintainer can tell why an upload failed ([PR \#99](https://github.com/eclipse-csi/pia/pull/99)).  
* Availability: The DependencyTrack upload had no timeout, and because the handlers are asynchronous while the HTTP client blocks, an unresponsive DependencyTrack would stall the whole event loop — the pod would stop serving everything, liveness probe included, until restarted. Connect and read timeouts were added, sized so multi-megabyte SBOMs still succeed ([PR \#95](https://github.com/eclipse-csi/pia/pull/95)).  
* Observability: A Prometheus endpoint was added, served on the application port and not routed publicly, instrumenting the request path, OIDC verification by phase, and upload duration and outcome. Every label value comes from a fixed set or a database row rather than unvalidated request input, so unrouted requests cannot mint unbounded series ([PR \#93](https://github.com/eclipse-csi/pia/pull/93)). Basic log collection through Grafana was enabled alongside it.   
* Releases: Versions 0.7.0 and 0.8.0 carried the fixes above into production ([PR \#100](https://github.com/eclipse-csi/pia/pull/100), [PR \#102](https://github.com/eclipse-csi/pia/pull/102)).

### Adopters

* New Project Onboarded at Scale: LocationTech GeoMesa began uploading SBOMs for 120 modules across nine products into DependencyTrack. In the first days of Prometheus scraping, PIA recorded 80 SBOM uploads, the large majority coming from the newly onboarded project.

# Open VSX

* Trusted Publishing Hardened: Trusted publishing was moved from hard-coded provider constants to configuration and several paths by which a registration could outlive its dependencies were closed ([PR \#2114](https://github.com/eclipse-openvsx/openvsx/pull/2114)). Trusted publishing tokens were narrowed to publishing actions only through a new composable scope mechanism ([PR \#2127](https://github.com/eclipse-openvsx/openvsx/pull/2127)). A token race that let an arbitrary subset of a release's target platforms succeed while CI still reported green was fixed ([PR \#2125](https://github.com/eclipse-openvsx/openvsx/pull/2125)), as was a foreign key violation that failed every trusted publishing publish while preserving the audit trail for long-lived tokens ([PR \#2122](https://github.com/eclipse-openvsx/openvsx/pull/2122)).  
* Access Tokens Moved Out of Query Parameters: Personal access tokens are now accepted via an `Authorization: Bearer` header, removing a standing leak path through server and proxy access logs, with the query parameter deprecated but still working for unmigrated clients ([PR \#2209](https://github.com/eclipse-openvsx/openvsx/pull/2209)). A legacy token lookup that could authenticate a presented value equal to another token's stored hash was scoped to genuine version-0 rows, with a regression test ([PR \#2247](https://github.com/eclipse-openvsx/openvsx/pull/2247)). A verification-side keyring now allows the token hash secret to be rotated — or adopted at all — without invalidating every token in the registry ([PR \#2162](https://github.com/eclipse-openvsx/openvsx/pull/2162), [PR \#2159](https://github.com/eclipse-openvsx/openvsx/pull/2159)), and token bodies were re-encoded so their structure stays legible to secret scanners ([PR \#2142](https://github.com/eclipse-openvsx/openvsx/pull/2142)).  
* Untrusted Input in Absolute URLs: Absolute URLs in responses were built from `X-Forwarded-*` headers taken as they arrived and cached under keys that did not include the host, so a forged host reached beyond the request that sent it. An explicit server URL setting now takes precedence, bounded by a trusted-proxies list ([PR \#2196](https://github.com/eclipse-openvsx/openvsx/pull/2196)).  
* Resource Exhaustion Paths Closed: Package signing no longer allocates several times the package size — a \~300 MB package had required roughly three quarters of a gigabyte ([PR \#2170](https://github.com/eclipse-openvsx/openvsx/pull/2170)) — and proxied spool files are deleted even when the client aborts ([PR \#2241](https://github.com/eclipse-openvsx/openvsx/pull/2241)).  
* SBOM Upload Repaired: The docker SBOM workflow had never run since being added in August, triggering on `registry_package` events that `GITHUB_TOKEN`\-authenticated pushes do not raise, so the server and web UI images had never reached DependencyTrack. It is now called directly from the release pipeline ([PR \#2224](https://github.com/eclipse-openvsx/openvsx/pull/2224)).  
* Deployment Integrity: A nightly job now restores the newest production snapshot to a throwaway instance, dumps it, restores that dump again and compares row counts per table, so producing the backup is itself the restore test ([PR \#13429](https://github.com/EclipseFdn/open-vsx.org/pull/13429)). Staging, test and production were separated into per-environment configuration profiles, having previously shared one baked-in file that left test and production running with staging's scanner hosts and token prefixes ([PR \#13408](https://github.com/EclipseFdn/open-vsx.org/pull/13408)).  
* Registry Moderation: 561 namespace claims were processed alongside removal, unpublish and purge requests.  
* Coverage Note: The CodeQL and Sonar workflows were removed from the core repository in favour of agentic code review ([PR \#2147](https://github.com/eclipse-openvsx/openvsx/pull/2147)), reducing automated static-analysis coverage. Worth tracking against the review coverage that replaced it.

# Otterdog

* Applied Configuration Correctness: Under the rebase merge strategy, only the last replayed commit of a pull request was being applied and nothing reported the remainder as missing — a silent gap between an approved organization configuration and what actually reached GitHub, now closed ([PR \#773](https://github.com/eclipse-csi/otterdog/pull/773)). Webhook events whose payload contained a null field were being dropped entirely before their hooks ran ([PR \#775](https://github.com/eclipse-csi/otterdog/pull/775)).  
* Validation and Drift: Code scanning language configuration can no longer be set on a repository that does not yet exist and therefore cannot be validated ([PR \#767](https://github.com/eclipse-csi/otterdog/pull/767)), and drift between declared and live settings was raised from a note to a warning ([PR \#765](https://github.com/eclipse-csi/otterdog/pull/765)).  
* Approval and Property Controls: Auto-merge approval teams became configurable rather than a hard-coded suffix match ([PR \#715](https://github.com/eclipse-csi/otterdog/pull/715)), and organization custom properties gained control over which actors may edit their values at the repository level ([PR \#642](https://github.com/eclipse-csi/otterdog/pull/642)). A cost check that had blocked auto-merge for all repository creations was corrected ([PR \#770](https://github.com/eclipse-csi/otterdog/pull/770)).  
* Releases and Throughput: Otterdog 1.5.0 and 1.6.0 were released, the latter adding a pull request statistics dashboard across Eclipse Foundation organizations ([PR \#752](https://github.com/eclipse-csi/otterdog/pull/752)). The dashboard reported a 50% auto-merge rate across 339 pull requests, and open pull requests were brought down to 14\.
