# Vulnerability Management

### AI-Assisted Scanning Campaign

* Findings Submissions: 60 findings from the AI-assisted scanning campaign over Eclipse project repositories were manually validated, deduplicated and submitted to projects, with 10 of them already resolved by the end of the month.  
* New Findings: The scanning campaign produced approximately 8k additional findings during the month, which have yet to be validated and deduplicated.  
* Validation Tooling: Bugs in the scanning and triage tooling were fixed, validation was split into smaller per-repository units, and the first-level triage interface and its runbook were reworked, which shortened the time needed to validate a finding. Findings confirmed as true positives at critical, high or medium severity now generate a patch file automatically, which is attached to the report so that projects receive a proposed fix.

### Report Handling

* Stale Report Follow-Up: Reports without activity for more than 30 days have been continuously pinged throughout the month.  
* CVE Publication: More than 20 CVEs were published over the course of the month.  
* Committer Guidance: The vulnerability handling guide for committers and project leads was updated with review feedback and shared with the projects team.

# SBOM

### Infrastructure

* Dependency-Track: The staging and production Dependency-Track servers were upgraded. A persistent Grafana dashboard now tracks SBOM uploads.

### Adopters

* Upload Migration: Migration pull requests to the new PIA-based upload were opened automatically for all repositories that generate SBOMs, and project leads were pinged on the open ones. Near the end of the month, 95% of the projects have been migrated to use the new mechanism.  
* SBOM Generation Tooling: Work continues on an AI-Assisted SBOM workflow tool. The tool is able to create GitHub Actions workflows that upload through PIA, covers a great array of corner cases discovered during experimenting, and can write workflows directly into local clones.   
* Coverage Dashboard: AI-Assisted tooling was developed to gather important metrics about SBOM coverage and adoption. Data from about 380 projects and 2,400 repositories was gathered into a dashboard of SBOM adoption. It estimates roughly 1,700 Eclipse products (about 30% container images and 20% Maven) against about 70 with an SBOM in the registry. The dashboard and the method behind it were presented to the projects team. The coverage skills were published in [eclipse-csi/skills](https://github.com/eclipse-csi/skills).

# PIA

### OIDC Verification Hardening

* SSRF Prevention on Key Discovery: The `jwks_uri` advertised by an OIDC issuer is now restricted to the already allowlisted issuer URL, with a path limited to unreserved characters and no `.` or `..` segments. One project's Jenkins instance on the shared `ci.eclipse.org` host can no longer point PIA at another project's signing keys. OIDC discovery and JWKS fetches also refuse HTTP redirects and require a 200 response, so a registered issuer can no longer use a 3xx to send PIA to an arbitrary host ([PR \#113](https://github.com/eclipse-csi/pia/pull/113)).  
* Resource Exhaustion Limits: Discovery and JWKS responses are capped at 1 MiB, counted after decompression so gzip bombs are covered, and reads stop after a 10-second deadline. Blocking authentication and upload I/O now runs off the event loop, so a slow or unreachable issuer ties up a single worker instead of stalling the service ([PR \#112](https://github.com/eclipse-csi/pia/pull/112)).  
* Malformed Token Handling: A JWT `iss` claim that is not a string now gets a 401 instead of a 500 ([PR \#109](https://github.com/eclipse-csi/pia/pull/109)).

### Input Validation & Logging

* Unauthenticated 500 Fix: A request body without a JSON Content-Type and with non-UTF-8 bytes caused a server error before authentication ran. A custom validation error handler now returns a 422, and error responses no longer echo the request body ([PR \#110](https://github.com/eclipse-csi/pia/pull/110)).  
* Log Injection Hardening: Following [GHSA-3g7j-3xgm-85mc](https://github.com/eclipse-csi/pia/security/advisories/GHSA-3g7j-3xgm-85mc), log escaping was extended to all remaining messages that include caller-controlled values, and a per-request ID in logs and response headers makes concurrent requests traceable ([PR \#106](https://github.com/eclipse-csi/pia/pull/106)).

# Otterdog

### Access Control & Configuration Integrity

* Team Access Removal: Removing a team from a repository's managed `team_permissions` produced no plan diff and was never applied, so revoked teams kept their GitHub access, as seen on a private repository in eclipse-score. Removals are now detected in plans and sync checks and applied ([PR \#842](https://github.com/eclipse-csi/otterdog/pull/842), [Issue \#841](https://github.com/eclipse-csi/otterdog/issues/841)).  
* Ruleset Integrity: A critical-severity bug made `apply` silently reset the "allowed merge methods" setting of pull-request rulesets, and `plan` could not see it. The setting is now compared and written back as configured ([PR \#777](https://github.com/eclipse-csi/otterdog/pull/777), [Issue \#768](https://github.com/eclipse-csi/otterdog/issues/768)).  
* Immutable Releases: GitHub immutable release settings are supported at organization and repository level, so published releases can no longer be modified after the fact ([PR \#665](https://github.com/eclipse-csi/otterdog/pull/665)).

### Policy Enforcement Reliability

* Blueprint Remediation: When one commit changed both a blueprint's description and configuration, only the description was stored, so policy checks ran against stale configuration and no remediation PRs were opened, as seen with `require-dependabot`. Both fields are now updated ([PR \#864](https://github.com/eclipse-csi/otterdog/pull/864)).  
* Service Resilience: Installation refresh tasks are bounded by a configurable concurrency limit. Previously a refresh across a few hundred organizations could exhaust memory and leave the web app in a restart loop ([PR \#843](https://github.com/eclipse-csi/otterdog/pull/843)).

### Supply Chain & Tooling

* Dependency Monitoring: npm dependencies of the web dashboard are tracked by Dependabot with a 7-day cooldown, and dedicated `python-security` and `npm-security` groups bring security fixes through separately ([PR \#820](https://github.com/eclipse-csi/otterdog/pull/820), [PR \#838](https://github.com/eclipse-csi/otterdog/pull/838)).  
* Agentic Workflow Threat Detection: The threat-detection step of the AI issue-triage workflow, which had stopped running after a partial action update, was restored with SHA256 binary pins, and an ignore rule prevents a repeat ([PR \#827](https://github.com/eclipse-csi/otterdog/pull/827)).  
* Configuration Playground: The dashboard Playground evaluates configurations in the browser and proposes changes from the user's own GitHub account, so the GitHub App needs no write permissions. JSON schemas reject values Otterdog does not allow ([PR \#878](https://github.com/eclipse-csi/otterdog/pull/878)).  
* Release 1.7.0: Otterdog 1.7.0 was released on October 27 ([commit 85a6310](https://github.com/eclipse-csi/otterdog/commit/85a6310ea38cd42fa565e1e93084ef0ab69c2446)).

# Open VSX

### Access Token & Publishing Security

* Scoped Access Tokens: Personal access tokens can now be limited to one namespace or a single extension, and a publish-only token type was added, so a leaked token exposes only what it was scoped to ([PR \#2296](https://github.com/eclipse-openvsx/openvsx/pull/2296), [Issue \#957](https://github.com/eclipse-openvsx/openvsx/issues/957)). The token dialog blocks generation while the scope input does not match a listed option, so a token cannot be created unscoped by mistake ([PR \#2313](https://github.com/eclipse-openvsx/openvsx/pull/2313)).  
* Duplicate Token Prevention: State-changing web UI requests are no longer retried automatically after a network error or 5xx, which could silently create duplicate tokens ([PR \#2363](https://github.com/eclipse-openvsx/openvsx/pull/2363), [PR \#2360](https://github.com/eclipse-openvsx/openvsx/pull/2360)).  
* Trusted Publishing Provenance: Versions published through trusted publishing record the workflow run ID, job workflow ref and commit SHA for GitHub, and the pipeline, job and SHA for GitLab, so each version traces back to the CI run that produced it ([PR \#2283](https://github.com/eclipse-openvsx/openvsx/pull/2283), [Issue \#2116](https://github.com/eclipse-openvsx/openvsx/issues/2116)).  
* CLI Credential Handling: The `follow-redirects` dependency was replaced with native Node HTTP, and the CLI now drops `Authorization`, `Cookie` and `X-OpenVSX-Token` headers on cross-origin redirects, which the old library forwarded. OIDC requests share this client and never send registry credentials to the CI token service ([PR \#2309](https://github.com/eclipse-openvsx/openvsx/pull/2309), [PR \#2322](https://github.com/eclipse-openvsx/openvsx/pull/2322)).

### Admin Access Control & Privacy

* Fine-Grained Admin Permissions: The single admin role was split into individual permissions for namespaces, extensions, scans, settings and reports, enabling least-privilege access ([PR \#2269](https://github.com/eclipse-openvsx/openvsx/pull/2269)).  
* Personal Data Handling: Eclipse-specific OAuth token and person-ID columns were removed from the core user table, a `UserForgottenEvent` lets a deployment erase personal data stored elsewhere when a user is anonymized, and database dump scrubbing clears leftover raw OAuth tokens ([PR \#2371](https://github.com/eclipse-openvsx/openvsx/pull/2371), [Issue \#2369](https://github.com/eclipse-openvsx/openvsx/issues/2369)).

### Malware, Secret & Namespace Scanning

* Secret Scanner Accuracy: Secret-detection rules are compiled case-sensitively as the gitleaks rule authors intended, removing false positives that blocked legitimate publications ([PR \#2330](https://github.com/eclipse-openvsx/openvsx/pull/2330), [Issue \#2329](https://github.com/eclipse-openvsx/openvsx/issues/2329)).  
* Scanner Reliability: Async scanner polling survives transient errors, 4xx error bodies can no longer be read as scan verdicts, and admins can review and release versions whose scans errored ([PR \#2307](https://github.com/eclipse-openvsx/openvsx/pull/2307), [PR \#2315](https://github.com/eclipse-openvsx/openvsx/pull/2315)). In production, a ClamAV timeout that discarded completed verdicts was fixed ([PR \#13800](https://github.com/EclipseFdn/open-vsx.org/pull/13800), [PR \#13801](https://github.com/EclipseFdn/open-vsx.org/pull/13801)). The YARA and ClamAV services stream uploads to disk instead of memory, removing out-of-memory crashes under load, and ClamAV was upgraded to 1.5.4 with CVE fixes for its archive and PE scanners ([PR \#14798](https://github.com/EclipseFdn/open-vsx.org/pull/14798), [PR \#14779](https://github.com/EclipseFdn/open-vsx.org/pull/14779)).  
* Namespace Ownership Verification: The publish-time namespace ownership check against the VS Code Marketplace was enabled in production, guarding against impersonation of established Marketplace publishers ([PR \#14198](https://github.com/EclipseFdn/open-vsx.org/pull/14198)). Nearly 900 namespace ownership claims were reviewed and processed during the month.  
* Blocklist Update: Four malicious extensions were added to the registry blocklist ([commit 94920a8](https://github.com/EclipseFdn/publish-extensions/commit/94920a888ff2c561e971ecdd9b709e0be44bd63e)).

The analytics database moved to a highly available CloudNativePG cluster with continuous WAL archiving and daily backups, in staging and production ([PR \#14256](https://github.com/EclipseFdn/open-vsx.org/pull/14256), [PR \#14765](https://github.com/EclipseFdn/open-vsx.org/pull/14765)).
