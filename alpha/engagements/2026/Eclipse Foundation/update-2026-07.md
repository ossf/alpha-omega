# Supporting EU Cyber Resilience 

As part of ongoing efforts to strengthen cybersecurity coordination across the EU, the team participated on a voluntary basis in the early testing of ENISA’s Single Reporting Platform (SRP) incident reporting platform ahead of its operational launch. This launch is scheduled for September 11, when the first round of the CRA obligations kicks off. This involvement provided an opportunity to evaluate the platform's reporting workflows, assess its usability and interoperability with existing processes, and contribute practical feedback to support its refinement. 

# Otterdog

### Credential & Access Handling

* Token-only operations were made safer: several operations did not explicitly set the `only_token` parameter, causing Otterdog to resolve full web-UI credentials even when they were not needed. All operations now honor the `no_web_ui` flag and avoid looking up web-UI credentials when an operation does not require them, unblocking token-only (GitHub App) setups and reducing unnecessary credential exposure ([PR \#699](https://github.com/eclipse-csi/otterdog/pull/699), [Issue \#693](https://github.com/eclipse-csi/otterdog/issues/693)).  
* MongoDB connections now pass the full URI so PyMongo uses the intended `authSource` rather than silently defaulting to `admin`, fixing an authentication failure mode for non-admin database users ([PR \#702](https://github.com/eclipse-csi/otterdog/pull/702)).

### Compliance & Policy Controls

* Added support for the `prevent_self_review` setting on deployment environments, which stops the user who triggered a deployment from approving their own deployment when required reviewers are configured — a common separation-of-duties compliance requirement now expressible as code ([PR \#641](https://github.com/eclipse-csi/otterdog/pull/641), [Issue \#680](https://github.com/eclipse-csi/otterdog/issues/680)).  
* Added support for environment variables and secrets in the configuration model, allowing environment-scoped secrets to be managed declaratively and reviewably ([PR \#689](https://github.com/eclipse-csi/otterdog/pull/689), [Issue \#537](https://github.com/eclipse-csi/otterdog/issues/537)).  
* Fixed status-check rulesets that are reported only by `integration_id`: `import` previously emitted a numeric token that `apply` misresolved as an app slug and 404'd, breaking enforcement of required status checks for app-reported checks ([PR \#700](https://github.com/eclipse-csi/otterdog/pull/700), [Issue \#695](https://github.com/eclipse-csi/otterdog/issues/695)).

### Workflow Pinning Robustness

* Hardened the `PinWorkflowTask` (which pins GitHub Actions to specific versions across managed repositories) so that malformed or invalid workflow YAML is handled gracefully instead of crashing the task, keeping action-pinning coverage intact across organizations with broken workflow files ([PR \#685](https://github.com/eclipse-csi/otterdog/pull/685), [PR \#684](https://github.com/eclipse-csi/otterdog/pull/684)).

### Release & Deployment

* A new [v1.4.0 release](https://github.com/eclipse-csi/otterdog/releases/tag/v1.4.0) was cut and deployed internally, rolling the above credential-handling, compliance, and workflow-pinning hardening into the version that manages projects’ GitHub organizations. The changelog was updated for the release [PR \#705](https://github.com/eclipse-csi/otterdog/pull/705) and local development was aligned to the accompanying Otterdog Helm chart 1.2.0 [PR \#706](https://github.com/eclipse-csi/otterdog/pull/706).

# Project Identity Authority (PIA)

### Identity & Token Validation

* Hardened OIDC issuer validation: `is_issuer_known` previously accepted any issuer whose string merely *started with* the expected `https://ci.eclipse.org` prefix. Because a prefix check treats the issuer as opaque text, crafted URLs such as a userinfo form (`https://ci.eclipse.org@other-host/...`) that resolve to a different host were accepted. Validation now parses the issuer and matches by scheme and host, closing an identity-spoofing vector ([PR \#62](https://github.com/eclipse-csi/pia/pull/62)).  
* Documented and clarified PIA's authorization scope in a prominent place in the README, reducing the risk of PIA being relied on beyond its intended trust boundary ([PR \#70](https://github.com/eclipse-csi/pia/pull/70)).

### Least-Privilege & Database Isolation

* Database migrations were moved out of application startup into a dedicated pre-rollout step (a Helm pre-install/pre-upgrade hook), so the long-lived application pods can run against a **read-only** database user instead of a schema-altering one — a significant reduction of the runtime blast radius ([PR \#61](https://github.com/eclipse-csi/pia/pull/61)).  
* Made existing and future migrations reversible so that a bad rollout can be cleanly rolled back; a migration had passed an unnamed constraint to `drop_constraint`, leaving it non-reversible ([PR \#80](https://github.com/eclipse-csi/pia/pull/80), [Issue \#78](https://github.com/eclipse-csi/pia/issues/78)).  
* Improved database connection resilience with `pool_pre_ping` and `pool_recycle`, so dropped pooled connections (idle timeouts, firewall reaps, failovers) are detected and transparently replaced rather than surfacing as availability failures ([PR \#65](https://github.com/eclipse-csi/pia/pull/65)).

### Authorization Lifecycle & SBOM Management

* Added `pia sync` and `pia create-dt-projects` CLI commands so that workload and DependencyTrack authorizations are driven from a reviewable curated file rather than one-off database writes. This makes authorizations auditable, revocable, and idempotent, replacing earlier per-invocation commands that left the database as the only (unreviewable) record ([PR \#68](https://github.com/eclipse-csi/pia/pull/68)); the superseded `add-workload` and `add-dt-project` commands were removed ([PR \#69](https://github.com/eclipse-csi/pia/pull/69)).  
* Restructured DependencyTrack project mapping so each Eclipse project maps to a single root DependencyTrack project with a non-empty product list, and enforced uniqueness with a `(ef_project_id, name)` constraint — ensuring SBOM/vulnerability data aggregates to exactly one project owner and cannot be silently misattributed ([PR \#82](https://github.com/eclipse-csi/pia/pull/82), [PR \#73](https://github.com/eclipse-csi/pia/pull/73), [Issue \#74](https://github.com/eclipse-csi/pia/issues/74)).  
* Set roll-up collection logic on created DependencyTrack projects so root projects aggregate their children and non-root projects aggregate children marked latest, giving accurate per-project vulnerability roll-ups ([PR \#76](https://github.com/eclipse-csi/pia/pull/76)).

### CI/CD Hardening

* Made the `zizmor` GitHub Actions static-analysis workflow exit non-zero on findings, so workflow-security findings now block a pull request instead of being informational only (a stopgap until rulesets are configured) ([PR \#83](https://github.com/eclipse-csi/pia/pull/83)).  
* Added a local DependencyTrack service to `docker-compose` with a bootstrap script for provisioning a scoped API token, enabling end-to-end testing of the sync flow without production credentials ([PR \#72](https://github.com/eclipse-csi/pia/pull/72), [PR \#77](https://github.com/eclipse-csi/pia/pull/77)).

# Open VSX

### Trusted Publishing & Credential Security

* Trusted Publishing Support: OIDC-based trusted publishing was introduced on the server, allowing namespace owners to register a trusted publisher (GitHub/GitLab provider, owner, repo, workflow, optional environment) so extensions can be published from a verified CI workflow instead of a long-lived Personal Access Token. Claims are resolved to stable provider IDs and stored in a dedicated table ([PR \#1980](https://github.com/eclipse-openvsx/openvsx/pull/1980)). Corresponding CLI support was in active development at month end.  
* PAT Masking: Personal Access Tokens are now masked in both the CLI and the web UI, preventing accidental disclosure of credentials on screen or in shared terminals ([PR \#1966](https://github.com/eclipse-openvsx/openvsx/pull/1966)).  
* Hardened Token Storage: The CLI replaced the archived and unmaintained `keytar` library with the actively maintained `cross-keychain` for token storage. The previous implementation could silently fall back to plaintext when the system keychain failed to bind; the new library removes that cross-platform failure mode ([PR \#1950](https://github.com/eclipse-openvsx/openvsx/pull/1950)).  
* Legacy PAT Path Removal: The dedicated PAT jOOQ repository was dropped in favor of the existing entity repository, reducing duplicate credential-handling code paths on the server ([PR \#1947](https://github.com/eclipse-openvsx/openvsx/pull/1947)).

### Malware Handling & Extension Control

* Malicious Extension Blocklist: The publish-extensions blocklist (`extensions.json`) was constantly updated throughout the month to add newly identified malicious extensions.  
* Deletion Logic Consolidation: The extension deletion logic in `ExtensionService` was consolidated and a race condition in the admin dashboard deletion flow was fixed, with the front end now re-fetching data on a 409 conflict — reducing the chance of inconsistent state when removing extensions ([PR \#1935](https://github.com/eclipse-openvsx/openvsx/pull/1935)).  
* Failed-Scan Enforcement: `ExtensionService.reactivateExtensions` was fixed so that extension versions with failed security scans are no longer reactivated when a publisher agreement is restored — the `active` state now correctly reflects scan outcomes and not only agreement status ([PR \#1952](https://github.com/eclipse-openvsx/openvsx/pull/1952)).  
* Safer Extension Control Defaults: Transitive deletion of malicious extensions' dependencies was made opt-in via a new `ovsx.extension-control.delete-transitively` flag defaulting to `false`, avoiding unintended cascading deletes ([PR \#1951](https://github.com/eclipse-openvsx/openvsx/pull/1951)). A related fix ensures the recurring extension-control job is actually stopped when the service is disabled, rather than continuing on its existing schedule ([PR \#1955](https://github.com/eclipse-openvsx/openvsx/pull/1955)).

### Namespace & Upload Integrity

* Namespace Impersonation Prevention: The registry now rejects namespace display names that collide with an existing namespace's name or display name, closing an impersonation/squatting vector where a namespace could masquerade as another ([PR \#1957](https://github.com/eclipse-openvsx/openvsx/pull/1957)).  
* Client-Side Upload Limits: A new `GET /api/config` endpoint was added and the client now rejects oversized extension uploads before transfer, limiting a resource-exhaustion vector at publish time ([PR \#1937](https://github.com/eclipse-openvsx/openvsx/pull/1937), [Issue \#1486](https://github.com/eclipse-openvsx/openvsx/issues/1486)).
